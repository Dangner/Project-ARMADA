# ARMADA — Adversarially Robust Adaptive Malware Detection Architecture Under Concept Drift

Immune-system-inspired static malware detection on **EMBER 2018** pre-extracted
feature vectors (2381-dim), with dual-discriminator domain adaptation,
test-time training, adversarial-robustness shield, immune memory and a
calibrated three-way decision engine.

> **Scope statement.** ARMADA operates on pre-extracted EMBER 2018 features of
> **Windows PE files only**. It does not support Linux/Android/macOS binaries,
> and the GUI/CLI never consumes raw executables.

## Data (real EMBER 2018 only)

ARMADA never generates synthetic data. Reported results are computed from
saved predictions produced on the official EMBER 2018 corpus:

1. Download `ember_dataset_2018_2.tar.bz2` (1.7 GB, sha256
   `b6052eb8d350a49a8d5a5396fbe7d16cf42848b86ff969b77464434cf2997812`)
   from the URL listed at <https://github.com/elastic/ember> and extract it
   into `data/ember2018/` (raw `train_features_*.jsonl`, `test_features.jsonl`).
2. Vectorise with the official extractor (exact benchmark features):

   ```bash
   pip install git+https://github.com/elastic/ember.git lief
   python -m armada.data.vectorize --data_dir data/ember2018 --with-test
   ```

   This writes `X_train.dat` (float32, 2381-dim rows), `y_train.dat`
   (labels: -1 unlabeled, 0 benign, 1 malware), `X_test.dat`/`y_test.dat`
   and `metadata.csv` (`sha256,appeared,label,subset`; `appeared` is the
   first-seen month `YYYY-MM`).
3. Alternatively, point `data.data_dir` in the config at an existing
   vectorised dump — `X_train.dat`, `y_train.dat`, `metadata.csv` are the
   only required files (`X_test.dat`/`y_test.dat` only when
   `data.include_test_subset: true`).

The temporal concept-drift split uses `metadata.csv` months: the **source**
domain is the earliest labeled months; later months become consecutive
target windows `T1..Tk` (drift severity grows with time). Unlabeled rows
(label -1) are used **only** as the unlabeled target pool for domain
adaptation / TTT. Scalers, feature selection and thresholds are fit on the
source period only — never on target data.

## Quick start

```bash
pip install -r requirements.txt

# Phase 1 (current): data prep + classical baselines (LR / RF / GBDT)
python -m armada.run --config configs/main.yaml --stage data
python -m armada.run --config configs/main.yaml --stage eval

# 5-minute smoke run (small caps; NOT for paper numbers)
python -m armada.run --config configs/fast.yaml --stage data --fast

# tests (dummy tensors live in tests/ only and never write to results/)
python -m pytest tests/ -q
```

Single entry point (stages appear as their phases land):
`python -m armada.run --config configs/main.yaml --stage {data,train,eval,ablate,robust,figures,all}`

## Outputs

- `results/` — `metrics_all.csv`, `metrics_by_window.csv`, `metrics_per_seed.csv`,
  `config_used.yaml`, `predictions/*.npz` (every metric is recomputed from
  these predictions; writers refuse any non-EMBER provenance).
- `figures/`, `tables/`, `REPORT.md` — generated by `--stage figures` (Phase 7).
- `cache/` — preprocessed `.npy` arrays keyed by a config hash.
- `logs/` — per-run logs with peak-RSS checkpoints.

## Reproducibility

- Fixed seeds (`seed_list` in the config); metrics reported as mean ± std over
  ≥ 3 seeds.
- Pinned `requirements.txt`; every hyperparameter lives in `configs/main.yaml`.
- Metrics suite: accuracy, precision, recall, F1, AUC-ROC, AUC-PR, TPR@FPR
  0.1 %/1 %, expected calibration error — computed by code from saved
  predictions, never hand-entered.

## Limitations (read before citing)

1. **Windows PE only.** EMBER 2018 features describe Windows Portable
   Executables. Nothing here transfers to Linux/Android/etc.
2. **Feature-space adversarial evaluation.** FGSM/PGD perturbations are
   applied to the 2381-dim feature vectors with EMBER constraints
   (count-like features kept non-negative, values clipped to valid ranges).
   Such perturbed vectors are **not guaranteed to correspond to valid PE
   files**; robustness numbers are feature-space measurements, not
   executable-space attack success rates.
3. **Scale limits.** Designed for ~8 GB RAM, CPU-first (CUDA optional).
   Sample caps (`n_train`, per-window caps) keep peak memory < 5 GB; the
   full 800K × 2381 matrix is never loaded at once. Scale study tops out at
   the caps your hardware allows (default 20K/50K/100K).
4. **Month resolution.** EMBER `appeared` dates are month-granular; drift
   windows are month blocks, not exact timestamps.
5. **Labels for evaluation only.** Target-window labels are used solely for
   final metrics; no supervised fitting ever sees target labels.

## Repository layout

```

  data/      loader.py (memmap, caps, source-only scalers, cache)
             groups.py (nine named EMBER groups, verified slices)

             ttt.py memory.py decision.py            (phases 2-5)

  eval/      metrics.py baselines.py ablation.py
             robustness.py stats.py
  viz/       style.py figures.py                     (phase 7)
  run.py     single entry point
configs/     main.yaml fast.yaml
tests/       unit + pipeline tests (dummy data confined here)
```

Legacy scripts (`01_vectorize_data.py` … `07_drift_simulation.py`,
`Armada_train_eval.py`, `mini_project_gui.py`) are kept as reference and are
superseded incrementally by the `armada/` package (same behaviour preserved).
